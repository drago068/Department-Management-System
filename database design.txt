# 📝 Attendance

This needs careful design.

I'd use:

```text
attendance_sessions
attendance_records
```

### `attendance_sessions`

Represents one class/period where attendance is taken.

```text
id
timetable_entry_id
date
staff_id
submitted_at
status
```

### `attendance_records`

Represents each student's attendance.

```text
id
attendance_session_id
student_id
status
marked_at
```

Status:

```text
PRESENT
ABSENT
ON_DUTY
```

Your frontend explicitly supports those three states. :chatgpt-content-reference{index="3"}

This design is better than putting everything into one giant attendance table because you can represent:

```text
September 27
    ↓
Period 3
    ↓
Deep Learning
    ↓
Faculty X
    ↓
III AI&DS-A
    ↓
Attendance Session
    ├── Student 001 → PRESENT
    ├── Student 002 → ABSENT
    ├── Student 003 → ON_DUTY
    └── ...
```

And you can enforce a uniqueness rule such as:

```text
UNIQUE(attendance_session_id, student_id)
```

to prevent duplicate records.

# 📄 Reports

I **wouldn't create a table for every report type**.

For example, don't create:

```text
defaulter_reports
faculty_reports
performance_reports
```

The reports can be generated from the underlying data.

For example:

```text
attendance_records
       ↓
Attendance Service
       ↓
Defaulters Report
```

and:

```text
timetable_entries
       ↓
Faculty Workload Service
       ↓
Faculty Workload Report
```

Your frontend specifies reports for low attendance, exam eligibility, faculty workload and academic performance. :chatgpt-content-reference{index="7"}

```text

ATTENDANCE
├── attendance_sessions

STUDY MATERIAL
├── materials

ACADEMIC PERFORMANCE
├── assessments

COMMUNICATION
├── announcements

SECURITY / AUDIT
└── audit_logs

PUBLIC CAMPUS
├── department_info
├── facilities
├── curriculum_items
├── research_publications
└── placement_statistics
```

### ⚠️ But don't create all of these blindly

This is the important part.

Your **frontend specification tells us what the application needs**, but it does **not establish the exact final database schema**. For example, it says the student dashboard displays internal marks and announcements, but doesn't specify all the database relationships behind them. :chatgpt-content-reference{index="9"}

So I would tell Antigravity:

> **Inspect the actual frontend source and mock data first. Then create the final ERD and schema. Do not create unnecessary tables just because they appear in this preliminary architecture.**

That will prevent over-engineering.

### My preferred relationship structure

The important chain is:

```text
Department
   │
   ├── Batch
   │     └── Section
   │           └── Students
   │
   └── Courses
          │
          └── Course Offering
                 │
                 ├── Faculty
                 └── Section
                        │
                        └── Timetable
                               │
                               └── Attendance Session
                                      │
                                      └── Attendance Records
                                             │
                                             └── Student
```

That structure gives you a **proper relational PostgreSQL design** instead of a collection of disconnected tables.

And yes—I'd make **the database/ERD the first actual backend deliverable** before letting Antigravity start generating FastAPI routers.
